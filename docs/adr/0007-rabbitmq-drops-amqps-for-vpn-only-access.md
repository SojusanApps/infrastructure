# RabbitMQ drops AMQPS/TLS in favor of binding directly to the VPN interface

[0003](./0003-shared-rabbitmq-broker-for-user-deletion-propagation.md) had RabbitMQ terminate its own TLS (AMQPS, port 5671) because the reverse proxy at the time was HTTP-only and couldn't do raw TCP passthrough. That's still true of the in-repo reverse proxy introduced in [0006](./0006-tls-terminated-by-in-repo-reverse-proxy.md), but the driving need for RabbitMQ's own TLS is gone regardless: with no Consuming App connected yet, and the already-deployed wg-easy VPN available as this repo's access-control boundary, we removed AMQPS entirely rather than carry forward a production cert story that was already incomplete (0003 never issued a real production cert for it).

RabbitMQ now speaks plain AMQP (5672) and serves its Management Console (15672) both bound directly to the WireGuard server's own tunnel address (`10.8.0.1`) instead of `0.0.0.0` — the same "bind to a specific host IP to restrict reachability" pattern this repo already used for wg-easy's own admin UI (`127.0.0.1:51821`). Traffic reaching either port is already inside the VPN's encrypted tunnel, so a second, independent TLS layer would only add cert-lifecycle burden without defending against a concrete threat. Any future Consuming App connecting to the Shared Broker must join the VPN as a WireGuard peer.
